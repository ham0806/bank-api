# 学習ノート

## TDD

1. Red: 失敗する業務ルールのテストを書く。
2. Green: 最小限の実装でテストを通す。
3. Refactor: 依存方向、命名、重複を整理する。

ドメインテストではDBやSpringを起動せず、PostgreSQLの制約やロックは統合テストで確認します。

## Clean Architecture

依存の向きは Adapter → Application → Domain です。内側は外側のクラス名を知りません。

- ドメインは口座残高や振込状態などの業務ルールだけを持ち、SpringやjOOQに依存しません。
- ユースケースは入力ポートとして公開し、Webとスケジューラは具象サービスではなくこの契約を呼びます。
- DBと外部金融機関は出力ポートの向こうに置き、Adapterで実装します。
- Outboxの取得・外部連携・確定/失敗はユースケースの手順であり、スケジューラは起動きっかけだけを持ちます。

`@Transactional`をapplication層に置くのは、学習用の実用的な境界です。厳密にフレームワークから切り離す場合は、トランザクション境界を別の仕組みへ移します。

## 冪等性

冪等性はアプリケーションのif文だけではなく、リクエストハッシュとDB一意制約で担保します。並列リクエストでは、一意制約の競合を正常系の再取得として扱います。

## 同時実行制御

楽観ロックのversionは競合を検出する補助線として保持し、金額を扱う更新では悲観ロックで口座行を先にロックします。複数口座を扱うときは全処理でロック順序を統一します。

## Transactional Outbox

DB更新とOutboxイベントの登録を同一トランザクションに入れます。外部API呼び出しはDBトランザクションの外で行い、処理結果を別トランザクションで確定します。

重要なのは、外部連携の成功・失敗だけでなく、成功後にレスポンスやワーカーが失われるケースを再実行可能にすることです。
